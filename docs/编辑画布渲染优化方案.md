# 编辑画布渲染优化方案

> 编辑 Tab：**mjml 编译照走 + HTML 直接挂 Shadow DOM + 段级 DOM 更新**。
> 不再经 `HtmlStringToReactNodes` 整树转 React（编辑侧多余的一层）。
> 相关：`render-cache`、`MjmlDomRender.tsx`、`HtmlStringToReactNodes.tsx`（将拆出 post-process，编辑侧废弃）

---

## 1. 核心结论（先看这个）

1. **编译 ①**：`JsonToMjml → mjml-browser → HTML` **不能省**（L1/L2/L3 减少重复编译），保证与预览/发信一致。
2. **挂载 ②（现状）**：`HtmlStringToReactNodes` 整页 `DOMParser` + 递归 `React.createElement` + `createPortal`——**对编辑画布是多余的一层**。
3. **挂载 ②（目标）**：`postProcessEmailHtml` → **直接写入 Shadow DOM**（`innerHTML` / 段级 `morphdom`），未变 section **不动 DOM**。
4. **交互不依赖 React**：Text 内联输入、选中、拖放本就靠 **contenteditable + Shadow DOM 事件委托**，与 React reconciliation 无关。
5. **预览 Tab** 可继续 `HtmlStringToPreviewReactNodes`（只读）；**仅编辑 Tab 去掉 React 挂载**。

---

## 2. 为什么编辑画布不必再转 React？

### 2.1 真正在干活的是 DOM，不是 React

| 能力 | 实现方式 | 是否依赖 React |
|------|----------|----------------|
| Text 画布内输入 | `contenteditable` + `shadowRoot` `input` 事件 | ❌ |
| 写回 JSON | `InlineText` 读 `innerHTML` → `form.change` | ❌ |
| 点击选中块 | `useDropBlock` 查 `node-idx` class | ❌ |
| 富文本工具栏 | `RichTextField` 读 `activeElement` 的 `data-content_editable-idx` | ❌ |
| L3 打字冻结 | 跳过重新挂载，保留当前 DOM | ❌ |

`HtmlStringToReactNodes` 实际只做两件事：

1. **后处理 HTML**：加 `node-idx`、`contenteditable`、merge tag Badge、链接 `tabIndex`
2. **把 HTML 递归建成 React 元素树**，再 `createPortal` 进 Shadow DOM

第 1 步必须保留（抽成 `postProcessEmailHtml`）；第 2 步对编辑画布**可删除**，改为 `innerHTML` / `morphdom` 即可。

### 2.2 Text 块内联输入链路（与 React 无关）

```
mjml → HTML
  → postProcess：text 块内部 div 加 contenteditable + data-content_editable-idx
  → 写入 Shadow DOM（innerHTML / morph）

用户点击 → 浏览器原生 contenteditable 聚焦
RichTextField → 读 activeElement 的 idx → 绑定 form Field
InlineText → shadowRoot 'input' → debounce → form.change(字段路径, innerHTML)

打字中 → L3 冻结 DOM，不重新挂载
```

## 3. 两段管线（目标态）

```
┌─────────────────────────────────────────────────────────────────┐
│ ① 编译段（不变）                                                  │
│    pageData → JsonToMjml → mjml → HTML 字符串                    │
│    缓存：L1 整页 / L2 段级 HTML / L3 富文本冻结                   │
└─────────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────────┐
│ ② 挂载段（改造）                                                  │
│    HTML → postProcessEmailHtml → Shadow DOM（innerHTML / morph） │
│    段级：未变 section 不更新 DOM                                  │
│    ❌ 不再：HtmlStringToReactNodes → createPortal                │
└─────────────────────────────────────────────────────────────────┘
```

| 阶段 | 当前 | 目标 |
|------|------|------|
| ① 编译 | L1/L2/L3 + mjml | 保持 |
| ② 挂载 | 整页转 React 树 | **postProcess + 直接 DOM** |
| ② 缓存 | 无 | **段级 DOM 保留 / morph 跳过** |

---

## 4. 缓存分层（L1/L2/L3 + M1）

| 层级 | 优化段 | 做什么 |
|------|--------|--------|
| **L3** | ① + ② | 富文本聚焦：冻结 DOM，不编译、不挂载 |
| **L1** | ① | Undo 等：整页 HTML 命中，零编译 |
| **L2** | ① | 只重编译变了 section 的 HTML，再拼接 |
| **M1（待做）** | ② | 段级 DOM：未变 section **不 innerHTML / 不 morph** |

L2 优化「HTML 从哪来」；M1 优化「HTML 怎么进 Shadow DOM」。两层正交，都要做才打通全链路。

---

## 5. 段级 DOM 挂载方案（首选）

### 5.1 总体流程（先计划，再合并挂载）

DOM 挂载**要做优化**：避免「逐段 parse → 逐段 replace」触发多次 layout。采用 **两阶段提交**：

```
pageData 变化
    │
    ▼
① compileWithRenderCache → fullHtml
    │
    ▼
②-a 准备（内存，不触达 Shadow DOM）
    postProcessEmailHtml(fullHtml) 一次        // 整页只 post-process 一次
    collectRenderSegments + 比对 subtreeHash   // 产出 MountPlan
    │
    ▼
②-b 构建片段（仍不触达页面）
    对 plan 中「需更新」的段：
      parse 段 HTML → DocumentFragment
    PageChrome 变了 → 单独构建 chrome Fragment
    │
    ▼
②-c 合并提交（一次或少量写 DOM）
    requestAnimationFrame 内批量 replace / append
    未变段：不读写
    变了段：liveNode.replaceWith(fragment) 或段槽位替换
```

**原则**：先算清改哪些段 → 在内存里建好 Fragment → **合并写入 Shadow DOM**，减少 reflow / 打断 contenteditable。

### 5.2 合并挂载（Merged Mount）要做什么？

| 问题 | 朴素做法 | 合并挂载 |
|------|----------|----------|
| post-process | 每段各 parse 一次整页 | **整页 postProcess 一次**，再按 idx 切片段 |
| 写入 Shadow DOM | 循环 N 次 `innerHTML` / `replaceChild` | 先建 **DocumentFragment**，再 **一次** 替换或 rAF 内批量提交 |
| 布局抖动 | 每改一段触发 reflow | 多段变更合并为 **单次 commit** |
| 与 L2 对齐 | 重复 diff | 共用 `subtreeHash`，MountPlan 与 L2 段列表一致 |

#### MountPlan 结构（示意）

```ts
interface SegmentMountPlan {
  mode: 'full' | 'segment';       // 结构变更 → full
  pageChromeChanged: boolean;
  segments: Array<{
    idx: string;
    subtreeHash: string;
    action: 'skip' | 'replace' | 'insert' | 'remove';
    // replace/insert 时附带已 post-process 的 outerHTML 或预建 Fragment
  }>;
}
```

#### 先创建 Fragment，再挂载

```ts
function htmlToFragment(segmentOuterHtml: string): DocumentFragment {
  const template = document.createElement('template');
  template.innerHTML = segmentOuterHtml.trim();
  return template.content; // DocumentFragment，未插入文档，不触发 layout
}

function commitSegmentReplace(liveNode: Element, fragment: DocumentFragment) {
  liveNode.replaceWith(fragment); // 单段一次 reflow 边界
}

// 多段连续变更：可先收集 replacements，再在 rAF 里顺序执行
function commitMountPlan(plan: SegmentMountPlan, shadowRoot: ShadowRoot) {
  requestAnimationFrame(() => {
    if (plan.mode === 'full') {
      shadowRoot.innerHTML = plan.fullBodyHtml!;
      return;
    }
    if (plan.pageChromeChanged) {
      applyPageChrome(shadowRoot, plan.chromeFragment!);
    }
    for (const item of plan.segments) {
      if (item.action === 'skip') continue;
      const live = findElementByNodeIdx(shadowRoot, item.idx);
      if (live && item.fragment) {
        commitSegmentReplace(live, item.fragment);
      }
    }
  });
}
```

> **P0** 可先用整页 `innerHTML`（等价于 full + 单次 commit）；**P1** 再上 segment + Fragment 合并提交。

### 5.3 postProcess 与切片顺序（避免重复工作）

推荐顺序（**不要**「每段 extract 后再各 postProcess 一次」）：

```
fullHtml
  → postProcessEmailHtml(fullHtml)     // ① 一次
  → processedDoc
  → 对每个需更新的段：extractSegmentOuterHtml(processedDoc, idx)
  → htmlToFragment(segmentOuterHtml)   // ② 按段建 Fragment
  → commitMountPlan                    // ③ 合并写入
```

这样 contenteditable / node-idx 标记与整页 post-process 规则一致，且 DOMParser 只做 **1 次全页 + 仅变更段的 template 解析**。

### 5.4 postProcessEmailHtml（从 HtmlStringToReactNodes 抽出）

把现有 `HtmlStringToReactNodes` 里 **DOMParser 后处理** 抽成纯函数，**不** `React.createElement`：

```ts
// packages/email-editor-editor/src/canvas-mount/postProcessEmailHtml.ts

export function postProcessEmailHtml(
  html: string,
  options: { enabledMergeTagsBadge: boolean },
): string {
  const doc = domParser.parseFromString(html, 'text/html');

  // 链接 tabIndex、merge tag Badge
  // 识别 node-type / node-idx → makeStandardContentEditable / makeBlockNodeContentEditable
  // （逻辑自 HtmlStringToReactNodes 搬迁）

  return serializeDocument(doc);
}
```

**P0**：`shadowBody.innerHTML = extractBodyInnerHtml(postProcessed)`（单次 commit）。
**P1+**：按 MountPlan 对变更段 `replaceWith(fragment)`，未变段跳过。

### 5.5 段级更新策略（分期）

| 阶段 | 挂载方式 | commit 次数 |
|------|----------|-------------|
| **P0** | 整页 postProcess + 一次 `innerHTML` | 1 次（去掉 React） |
| **P1** | MountPlan + 变更段 Fragment + 批量 replace | 1 次 rAF 内 N 次 replace（N=变更段数） |
| **P2** | 变更段 morphdom（单段内细化，少替换节点） | 在 P1 的 replace 路径上可选 |

**不推荐**：逐段 `innerHTML` 且不合并 rAF；段级 `HtmlStringToReactNodes`。

> **性能续篇（2026-06-18）**：P1 段级 `postProcess` 已落地（~1.3ms/段）。下一步 **L2 段级直通挂载**（跳过整页 `replaceSegmentInHtml`，compile 直出 `segmentPatches`）见 [编辑画布-L2段级直通挂载方案.md](./编辑画布-L2段级直通挂载方案.md)，目标改 1 段颜色 **< 50ms**。

### 5.6 渲染段（Segment）

与 L2 共用 `collectRenderSegments(pageData)`：

- 颗粒度：section / hero / group（`SEGMENT_BLOCK_TYPES`）
- 每段：`idx` + `subtreeHash`
- 变了段：从 **已 post-process 的** 整页 HTML 提取片段 → `htmlToFragment` → 合并 commit

### 5.7 目标模块结构

```
packages/email-editor-editor/src/
  canvas-mount/
    postProcessEmailHtml.ts    # 整页后处理（一次）
    buildMountPlan.ts          # segments + prev hash → MountPlan
    htmlToFragment.ts          # outerHTML → DocumentFragment
    commitMountPlan.ts         # rAF 内合并写入 Shadow DOM
    EditCanvasMount.ts         # 入口：prepare → build fragments → commit
    PageChrome.ts              # head、body 外壳 Fragment
    types.ts                   # SegmentMountPlan

  utils/
    HtmlStringToReactNodes.tsx # 保留给预览或过渡期；编辑 Tab 不再调用
    HtmlStringToPreviewReactNodes.tsx  # 预览只读，可继续用
```

`MjmlDomRender` 职责：

```ts
const html = compileWithRenderCache(...);
// 旧：createPortal(HtmlStringToReactNodes(html), ref)
// 新：
editCanvasMount(ref, html, pageData, { enabledMergeTagsBadge });
```

`editCanvasMount` 内部用 **imperative DOM**，外层仍可用一个轻量 React 组件管 ref 生命周期。

### 5.8 何时降级整页 innerHTML（单次 commit）

| 场景 | 处理 |
|------|------|
| 冷启动 / 无 prev | 整页 postProcess + innerHTML |
| 增删 section、idx 漂移 | 整页重建（或 stableId 后优化） |
| condition/iteration 段 | 与 L2 一致，整页降级 |
| Page 全局样式变 | 只更新 PageChrome |
| 段 extract 失败 | 整页降级 |

### 5.9 埋点

```ts
perfReport('MjmlDomRender.mount', {
  mode: 'dom-full' | 'dom-segment',
  totalSegments: N,
  updatedSegments: K,
  skippedSegments: N - K,
  fragmentBuildMs: number,  // 建 Fragment 耗时（内存）
  commitMs: number,           // 写入 Shadow DOM 耗时
  commitBatches: 1,           // 目标恒为 1（rAF 单次提交）
  usedMorph: boolean,
});
```

期望（改 1 个 section 背景）：`updatedSegments: 1`，`skippedSegments: N-1`。

## 6. 案例 walkthrough

假设 L 档模板约 10 个 section，① 已有 L2。

---

### 案例 1：改 1 个 Section 背景色

| 步骤 | 模块 | 行为 |
|------|------|------|
| 1 | form | 更新 section[1] attributes |
| 2 | ① L2 | S0/S2… 段 HTML 缓存命中；仅 S1 编译；拼 `fullHtml` |
| 3 | ② M1 | S0、S2… `subtreeHash` 未变 → **DOM 不动** |
| 4 | ② prepare | 整页 postProcess 一次；MountPlan：仅 S1 `action=replace` |
| 5 | ② build | `htmlToFragment(S1)`（内存，无 layout） |
| 6 | ② commit | rAF 内 `S1_live.replaceWith(fragment)`；S0/S2 skip |

**耗时粗算**：① ~100ms + ② prepare/build ~5ms + commit ~5～15ms vs 现状 ② ~300ms（整页 React 解析）。

---

### 案例 2：Text 块画布内打字

| 阶段 | 行为 |
|------|------|
| 打字中 | **L3**：不编译、不挂载，保留当前 contenteditable DOM |
| input 事件 | `InlineText` 监听 shadowRoot，写回 form（**与改前相同**） |
| 失焦后 | S1 `subtreeHash` 变 → ① L2 编译 S1 → ② 只更新 S1 DOM |

去掉 React 整树重建后，失焦刷新范围更小，有利于保留体验。

---

### 案例 3：Undo

| ① | ② |
|---|---|
| **L1 命中**，零编译 | 全段 hash 与 Undo 前一致 → **零 DOM 更新** |

① + ② 同时命中，接近瞬时。

---

### 案例 4：冷启动

| ① | ② |
|---|---|
| 全量 mjml ~500ms | 整页 `postProcessEmailHtml` + innerHTML（一次） |

---

### 案例 5：末尾新增 Section

前 N 段 idx/hash 不变 → 前 N 段 DOM 保留，仅 append 新段 DOM（不必整页 React 重建）。

---

### 案例 6：删除中间 Section

idx 漂移 → ② 整页 DOM 重建；`stableId` 后可按 id 保留未删段。

### 案例 7：现状 vs 目标（案例 1）

```
【现状】
JSON → L2(1段) → fullHtml → HtmlStringToReactNodes(整页) → createPortal → 整树替换

【目标】
JSON → L2(1段) → fullHtml → postProcess
  → S0,S2…: DOM 不动
  → S1: 段 DOM 替换 / morph
```

## 7. 与预览 / 发信的关系

| 场景 | 编译 ① | 挂载 ② |
|------|--------|--------|
| **编辑 Tab** | L1/L2/L3 + mjml | **postProcess + 直接 DOM（M1）** |
| **预览 Tab** | L1/L2 + mjml | `HtmlStringToPreviewReactNodes` 或 iframe（只读，可保留 React） |
| **导出 / 发信** | JsonToMjml + mjml | 无编辑器挂载 |

权威 HTML 始终来自 **mjml-browser**；编辑画布只是更快、更轻地把同一份 HTML 放进 Shadow DOM。

---

## 8. 不是什么

| 误解 | 实际 |
|------|------|
| 去掉 React 挂载 = 去掉 mjml | ❌ 编译仍走 mjml |
| 必须手写 mj-table React | ❌ 不需要 |
| 段级方案 = 段级 HtmlStringToReactNodes | ❌ 已改为段级 **DOM** 更新 |
| 预览也要去掉 React | ❌ 仅编辑 Tab 改；预览可不动 |
| postProcess 可以不做 | ❌ node-idx、contenteditable 仍需要 |

## 9. 实施分期

### P0：去掉编辑侧 React 挂载（功能等价）

- [ ] 抽出 `postProcessEmailHtml`（自 `HtmlStringToReactNodes`）
- [ ] `MjmlDomRender`：整页 `innerHTML` 替代 `createPortal(HtmlStringToReactNodes)`
- [ ] 回归：选中、拖放、Text 输入、工具栏、merge tag、L3

### P1：段级合并挂载（性能）

- [ ] `buildMountPlan` + `commitMountPlan`（先 Fragment，再 rAF 批量 commit）
- [ ] 整页 `postProcessEmailHtml` 一次，再按段切片
- [ ] `htmlToFragment`；未变段 skip；变更段 `replaceWith(fragment)`
- [ ] `PageChrome` 与 page 级指纹分离
- [ ] 埋点 `fragmentBuildMs` / `commitMs` / `commitBatches`

### P2：增强（可选）

- [ ] 段级 morphdom（验证 contenteditable 焦点）
- [ ] 末尾 append section 增量 DOM
- [ ] `stableId` 减少结构变更降级
- [ ] mjml 快照 codegen（升级回归，见 §10）

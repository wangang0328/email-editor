# 渲染缓存说明

> 模块路径：`packages/email-editor-editor/src/render-cache`  
> 统一编译入口：`compileWithRenderCache()`（`compilePipeline.ts`）  
> 全局管理器：`getRenderCacheManager()`（`RenderCacheManager.ts`）  
> 浏览器调试：`window.__EE_RENDER_CACHE__`

---

## 1. 背景与目标

邮件编辑器每次内容变更默认走完整渲染管线：

```
pageData → JsonToMjml → mjml-browser → HTML →（canvas-mount 直接 DOM 挂载）
```

L 档模板单次全量编译约 **470ms+**，是 Undo、改属性、块操作卡顿的主因。

**三级缓存**在编译层（① JsonToMjml + mjml）按不同颗粒度复用 HTML，与下游 DOM 挂载（canvas-mount / M1）正交：

| 层级 | 颗粒度 | 典型收益场景 |
|------|--------|--------------|
| **L1** | 整页 HTML | Undo 回退到历史快照、content 完全未变 |
| **L2** | Section HTML 片段 | 只改一个 section 属性（部分结构缓存） |
| **L3** | 运行时冻结 HTML | 富文本输入中跳过重复编译 |

实测（L 档场景 3 改色 5 次）：改造前 `pipelineMs` 中位数 **294.4ms** → 改造后 **21.7ms**（`cacheHitLevel=L2`）。详见 `docs/PERF_BASELINE.md`。

---

## 2. L1 / L2 / L3 对比

| | L1 整页 | L2 段级 | L3 运行时 |
|---|---------|---------|-----------|
| **存什么** | 完整 HTML 字符串（+ 可选 mjmlString） | 单个 section 的 `outerHTML` 片段 | 当前帧冻结的整页 HTML |
| **Key / 判定** | `buildPageCacheKey(pageData + profile + dataSource + …)` | `segmentIdx + subtreeHash + profile + dataSource + …` | `pageFingerprint` 是否与快照一致 |
| **存储结构** | `LruStore<PageCacheEntry>`，最多 32 条 | `LruStore<SegmentCacheEntry>`，最多 256 条 | 单对象 `l3Snapshot`（非 LRU） |
| **何时写入** | L2 组装成功 / 全量 miss 后 | 全量 miss 后 seed；单段重编译后 setL2 | 每次编译成功后 `preserveDom` |
| **何时命中** | 当前 page 与 key 完全一致 | page 变了，但部分段 `subtreeHash` 未变 | 富文本聚焦中且 page 指纹未变 |
| **典型 hitLevel** | `L1` | `L2` | `L3` |

### L2 ≠ 结构增量 diff

- **L2**：按段查 LRU，命中则复用 HTML；未命中则单段编译后 `replaceSegmentInHtml` 拼回 `baselineHtml`。
- **结构增量 diff（已移除）**：对 prev/current 做 added/removed/move 分类。当前不做增删移分类。

---

## 3. 缓存在哪？

所有缓存均在**浏览器主进程内存**中，由 `RenderCacheManager` 单例持有，**不落盘、不跨 Tab 共享**。

```
getRenderCacheManager()  ──▶  RenderCacheManager（模块级单例 globalManager）
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
              l1Store           l2Store        l3Snapshot
           LruStore Map       LruStore Map     单个对象或 null
           max 32 条           max 256 条
```

| 存储 | 类型 | 容量 | 代码 |
|------|------|------|------|
| L1 | `Map<string, PageCacheEntry>` + LRU 顺序 | 32 | `constants.ts` → `L1_CACHE_MAX_ENTRIES` |
| L2 | `Map<string, SegmentCacheEntry>` + LRU 顺序 | 256 | `constants.ts` → `L2_CACHE_MAX_ENTRIES` |
| L3 | `DomPreserveSnapshot \| null` | 1 | 无容量限制，随 `releaseDomPreserve` 清空 |

`LruStore`（`lruStore.ts`）：`get`/`set` 时把 key 移到 Map 末尾；超容量时删除**最久未使用**的 key。

调试挂载：初始化后 `window.__EE_RENDER_CACHE__ = manager`，可调用 `getStats()` / `clear()`。

**共享范围**：`MjmlDomRender`（edit profile）与 `PreviewEmailProvider`（preview profile）共用同一 manager，但 **L1/L2 key 含 `profile` 字段**，编辑与预览缓存互不干扰。

## 4. Hash 与 Key 计算详解（`hash.ts`）

所有 L1/L2 Map key、L2 段子树指纹、L3 页指纹，都遵循同一套两步管线：

```
业务对象  →  stableStringify()  →  确定性长字符串  →  hashString()  →  短 key（base36）
```

代码位置：`packages/email-editor-editor/src/render-cache/hash.ts`。

---

### 4.1 第一步：`stableStringify` — 稳定序列化

**目的**：相同语义的内容必须产出**完全相同**的字符串，否则缓存会误 miss 或误 hit。

**规则**（递归）：

| 输入类型 | 处理方式 |
|----------|----------|
| `null` / 原始类型 | 直接 `JSON.stringify` |
| 数组 | `[item0,item1,…]`，每项递归 |
| 对象 | key **字母序排序**后 `{key:value,…}`，value 递归 |

**示例**：

```ts
// 以下两种对象 stableStringify 结果相同
stableStringify({ b: 2, a: 1 })
// → '{"a":1,"b":2}'

stableStringify({ a: 1, b: 2 })
// → '{"a":1,"b":2}'
```

**与 `JSON.stringify` 的差异**：

- 普通 `JSON.stringify` 不保证 key 顺序 → 同一 page 两次 clone 可能 hash 不同。
- `undefined` 字段：对象中值为 `undefined` 的 key 仍会出现在 `Object.keys` 里；若业务侧删 key vs 设 `undefined`，结果可能不同（与 lodash `cloneDeep` 行为一致即可）。

**`pageData` / `IBlockData` 序列化范围**：

整棵块树递归进入 `stableStringify`，每个块节点包含：

```ts
{
  type: string;           // 如 'advanced_section'
  data: { value: … };     // 块业务数据（含富文本 content 等）
  attributes: { … };      // MJML 属性（background-color、padding…）
  children: IBlockData[]; // 子块数组，递归
}
```

不包含：`idx` 路径字符串（idx 仅在 L2 key 中单独字段 `segmentIdx` 传入，不写入 `hashBlockSubtree` 的 block 对象里）。

---

### 4.2 第二步：`hashString` — 短 key 生成

**算法**：djb2 xor 变体（32 位无符号整数），适合主线程同步计算，无 crypto 开销。

```ts
function hashString(input: string): string {
  let hash = 5381;                              // 初始种子
  for (let i = 0; i < input.length; i += 1) {
    hash = (hash * 33) ^ input.charCodeAt(i);   // hash × 33 ⊕ 当前字符码点
  }
  return (hash >>> 0).toString(36);             // 转无符号 32 位 → base36 字符串
}
```

**特性**：

| 项 | 说明 |
|----|------|
| 输出形态 | 短字符串，如 `"k7x2m9"`、`"1a2b3c"`（长度通常 6–7 字符） |
| 碰撞 | 非密码学 hash；工程上假定碰撞可忽略，LRU 存的是完整 HTML 不会串页 |
| 确定性 | 同输入字符串 → 同输出（跨会话、跨机器一致） |

**手算示意**（不必真算，理解管线即可）：

```
stableStringify({ engine:'1.0.2', profile:'edit', page:{…}, … })
  → 很长 JSON 字符串（可能数十 KB，L 档模板）
  → hashString(该字符串)
  → "x8f3k2"   // 作为 l1Store Map 的 key
```

---

### 4.3 四种 Hash / Key 函数对照

| 函数 | 输入 | 含 `engine` | 含完整 `page` | 含 `segmentIdx` | 含 `subtreeHash` | 用途 |
|------|------|-------------|---------------|-----------------|------------------|------|
| `hashBlockSubtree(block)` | 单个段根块 | ✗ | ✗（仅该段子树） | ✗ | —（输出即 subtreeHash） | 判断段内容是否变化 |
| `buildPageCacheKey` | `RenderCacheKeyInput` | ✓ | ✓ | ✗ | ✗ | **L1** Map key |
| `buildSegmentCacheKey` | idx + subtreeHash + input | ✓ | ✗ | ✓ | ✓（作为字段） | **L2** Map key |
| `buildPageFingerprint` | 同 L1 但无 engine | ✗ | ✓ | ✗ | ✗ | **L3** 快照比对 |
| `hashDataSource` | mergeTags 对象 | ✗ | ✗ | ✗ | ✗ | 辅助；空对象返回 `'0'` |

---

### 4.4 `subtreeHash` — 段子树指纹（`hashBlockSubtree`）

```ts
hashBlockSubtree(block: IBlockData): string {
  return hashString(stableStringify(block));
}
```

**计算对象**：`collectRenderSegments` 返回的**段根块**整棵子树（section + 其下所有 column/text/image…）。

**示例**：

```
用户选中 column，改 background-color
  → column.attributes 变化
  → 父 section 的 block 子树（含 children）内容变化
  → subtreeHash(section) 从 "abc123" 变为 "def456"
  → L2 key 中 subtreeHash 字段变 → getL2 miss → 单段重编译
```

**未变更的 section**：`subtreeHash` 不变 → 同一 `segmentIdx + subtreeHash` → L2 hit。

**注意**：`subtreeHash` 不含 `segmentIdx`。同内容 section 若在不同路径（极少见）hash 相同，但 L2 key 还有 `segmentIdx` 字段区分。

---

### 4.5 L1 Key — `buildPageCacheKey`

**调用链**：

```ts
// compilePipeline.ts
const l1Key = cache.buildL1Key(keyInput);
// → buildPageCacheKey(input)
// → hashString(stableStringify({ engine, profile, page, dataSource, breakpointOverride, keepClassName }))
```

**参与计算的字段**（`stableStringify` 对象，key 字母序）：

| 字段 | 来源 | 变化时效果 |
|------|------|------------|
| `breakpointOverride` | 预览 Tab 调整后的 breakpoint | L1 miss |
| `dataSource` | `mergeTags` / `previewInjectData` 深拷贝 | mergeTag 值变 → miss |
| `engine` | `RENDER_ENGINE_VERSION`（`constants.ts`） | 发版 bump → 旧缓存全部 miss |
| `keepClassName` | 预览 `true`；编辑不传 | 预览专用 |
| `page` | 完整 `pageData` 块树 | **任意块/属性变更** → miss |
| `profile` | `'edit'` \| `'preview'` | 编辑与预览隔离 |

**未参与 L1 key 的因素**：

- `baselineHtml`（仅 L2 组装用，不进 key）
- DOM / 挂载状态 / `renderVersion`
- 块在画布上的选中态

**命中语义**：当前请求的「编译输入」与某次历史写入 L1 时**完全一致** → 直接返回缓存 HTML，跳过 JsonToMjml。

---

### 4.6 L2 Key — `buildSegmentCacheKey`

**调用链**：

```ts
// RenderCacheManager.ts
buildL2Key(segmentIdx, subtreeHash, keyInput)
  → buildSegmentCacheKey(segmentIdx, subtreeHash, input)
  → hashString(stableStringify({
       breakpointOverride,
       dataSource,
       engine,
       keepClassName,
       profile,
       segmentIdx,
       subtreeHash,
     }))
```

**与 L1 的差异**：

| 对比项 | L1 | L2 |
|--------|----|----|
| 是否含整页 `page` | ✓ 完整树 | ✗ 仅 `subtreeHash` 代表段内容 |
| 是否含 `segmentIdx` | ✗ | ✓ 块路径 |
| 存储 value | 整页 HTML | 单段 `outerHTML` 片段 |
| page 局部变更 | 整页 miss | 仅变更段 `subtreeHash` 变 → 该段 miss，其余 hit |

**同一 section 改两次颜色**：

```
改色 #1: subtreeHash = H1 → L2 key K1 → 编译后 setL2(K1, fragment1)
改色 #2: subtreeHash = H2 → L2 key K2 → miss，重编译，setL2(K2, fragment2)
Undo 回 #1: subtreeHash 回到 H1 → getL2(K1) 仍可能命中（LRU 未淘汰）
```

**`hashDataSource` 在 L2 中的角色**：`dataSource` 整对象嵌入 key 对象后统一 `stableStringify`；若为空则 `dataSource: {}`。独立函数 `hashDataSource` 返回 `'0'` 仅作辅助，**L2 key 实际用 `dataSource ?? {}` 全量序列化**。

---

### 4.7 L3 指纹 — `buildPageFingerprint`

```ts
buildPageFingerprint(pageData, profile, dataSource, extras)
  → hashString(stableStringify({
       page: pageData,
       profile,
       dataSource: dataSource ?? {},
       breakpointOverride: extras?.breakpointOverride,
       keepClassName: extras?.keepClassName,
     }))
```

**与 L1 key 的差异**：**不含 `engine`**。

**原因**：L3 只回答「富文本聚焦期间 page 是否被改过」；引擎版本升级不应在失焦瞬间误清快照。发版后首次编译会走 L1/L2/miss 正常失效。

**比对时机**（`RenderCacheManager.tryL3`）：

```ts
if (buildPageFingerprint(当前 input) !== l3Snapshot.pageFingerprint) {
  l3Snapshot = null;
  return null;
}
return l3Snapshot.html;
```

### 4.8 端到端 Key 计算示例（改 1 个 section 背景色）

假设 L 档模板 34 段，用户改 `content.children.[1]` 的 column 背景色。

**1. 收集段**（`collectRenderSegments`）

```
segments[0]: idx=content.children.[0], subtreeHash=Ha, cacheable=true
segments[1]: idx=content.children.[1], subtreeHash=Hb' (变了), cacheable=true
segments[2]: idx=content.children.[2].children.[0], subtreeHash=Hc, …
…
```

**2. L1 查找**

```ts
l1Key = hashString(stableStringify({
  engine: '1.0.2',
  profile: 'edit',
  page: <整页新 pageData>,
  dataSource: { … },
  breakpointOverride: undefined,
  keepClassName: undefined,
}))
// → "p9k2xm"  →  l1Store.get("p9k2xm")  →  undefined（page 已变）→ miss
```

**3. L2 组装循环**（`assembleFromSegmentCache`）

```
segment[0]: l2Key = hashString({…, segmentIdx:'content.children.[0]', subtreeHash:Ha, …})
            → getL2 hit → continue

segment[1]: l2Key = hashString({…, segmentIdx:'content.children.[1]', subtreeHash:'Hb', …})
            → getL2 miss（仍是旧 hash Hb 的 key，或新 hash Hb' 无条目）
            → 单段编译 → setL2(新 key with Hb', 新 fragment) → replaceSegmentInHtml

segment[2..33]: 同 segment[0]，subtreeHash 未变 → hit
```

**4. L2 成功后回填 L1**

```ts
setL1(l1Key, { html: assembledFullHtml })  // 用步骤 2 的同一 l1Key
```

### 4.9 设计取舍与注意点

| 话题 | 说明 |
|------|------|
| 为何不用 `JSON.stringify(page)` 直接当 key | 太长（L 档 60KB+），Map 查找与内存占用差 |
| 为何不哈希碰撞用全量比对 | 碰撞概率极低；命中后仍返回缓存 HTML，由业务保证 key 输入一致 |
| `page` 引用变、内容同 | `stableStringify` 按值序列化，内容相同则 key 相同 |
| `page` 内容同、引用同 | L1 hit，与预期一致 |
| 编辑 vs 预览 | `profile` 进入 key，两套 HTML（testing / production）不混用 |
| 引擎发版 | bump `RENDER_ENGINE_VERSION` → 所有 L1/L2 key 变 → 冷 miss 一轮 |

## 5. 什么是 Section？如何收集？（`segments.ts`）

L2 的「段」不是任意块，而是邮件纵向结构中的 **section 级根块**。

### 5.1 段类型白名单 — `SEGMENT_BLOCK_TYPES`

```ts
BasicType.SECTION | HERO | GROUP
AdvancedType.SECTION | HERO
```

### 5.2 收集算法 — `collectRenderSegments(pageData)`

从 `content`（page 根）向下 DFS：

1. 当前块 type ∈ `SEGMENT_BLOCK_TYPES` → 作为一段，`idx` 为块路径（如 `content.children.[2].children.[0]`），**不再向下拆分**。
2. 否则（如 `wrapper`、`page`）→ 继续遍历 `children`。

返回 `RenderSegment[]`：

```ts
{
  idx: string;           // 块路径，与 node-idx class 一致
  block: IBlockData;     // 段根块引用
  subtreeHash: string;  // hashBlockSubtree(block)
  cacheable: boolean;   // 子树是否含 condition/iteration
}
```

### 5.3 不可缓存段 — `NON_CACHEABLE_DESCENDANT_TYPES`

子树含 `condition` / `iteration` / `advanced_condition` / `advanced_iteration` 时 `cacheable=false`：

- **不写入** L2 seed
- **不读取** L2 缓存
- assemble 时仍**单段重编译**，但不影响其他 `cacheable` 段的 L2 命中

### 5.4 示例（Shop Newsletter L 档）

page 下直接 2 个 section + 1 个 wrapper（内嵌 ~30 个 section）→ 约 **34 个** `RenderSegment`，与 `getStats().l2.size` 一致。

## 6. L1：如何缓存整页？

### 6.1 缓存条目 — `PageCacheEntry`

```ts
{
  html: string;        // 整页 MJML 编译结果
  mjmlString?: string; // 全量 miss 时保留，L2 组装路径可为空
  createdAt: number;
}
```

### 6.2 读取流程

```
compileWithRenderCache()
  → l1Key = buildPageCacheKey(keyInput)
  → entry = cache.getL1(l1Key)    // LruStore.get，命中则 stats.l1.hits++
  → 有 entry → return { html: entry.html, hitLevel: 'L1' }
  → 无 entry → recordL1Miss()，继续尝试 L2
```

### 6.3 写入流程

| 触发路径 | 代码位置 | 说明 |
|----------|----------|------|
| L2 组装成功 | `compilePipeline.ts` → `cache.setL1(l1Key, { html: assembled.html })` | 把组装结果缓存为当前 page 的 L1 |
| 全量 miss | `compilePipeline.ts` → `cache.setL1(l1Key, { html, mjmlString })` | 全量编译后写入 |

### 6.4 典型命中场景

- **Undo / Redo** 回到曾编译过的 `pageData` 快照 → L1 直接返回，~0ms 级。
- 连续两次触发编译且 `pageData` 引用/内容完全相同（少见）。

---

## 7. L2：如何缓存 Section？

L2 是**两层配合**：LRU 里存片段 + 调用方 ref 里存**上一帧整页 HTML**（`baselineHtml`）。

### 7.1 缓存条目 — `SegmentCacheEntry`

```ts
{
  segmentIdx: string;   // content.children.[n]…
  html: string;         // 该段根元素 outerHTML（含 node-idx class）
  subtreeHash: string;  // 写入时的子树 hash
  createdAt: number;
}
```

片段通过 `extractSegmentOuterHtml(fullHtml, segmentIdx)` 从整页 HTML 中按 `node-idx-{idx}` class 定位根元素并取 `outerHTML`。

### 7.2 写入路径 A：全量 seed — `seedL2FromFullHtml`

**时机**：`hitLevel=miss` 全量编译成功后。

```
for each segment in collectRenderSegments(pageData):
  if !segment.cacheable → skip
  fragment = extractSegmentOuterHtml(fullHtml, segment.idx)
  key = buildL2Key(segment.idx, segment.subtreeHash, keyInput)
  l2Store.set(key, { segmentIdx, html: fragment, subtreeHash, createdAt })
```

冷启动一次全量编译 → L2 中 seed 约 34 条（L 档）。

### 7.3 写入路径 B：单段重编译 — `assembleFromSegmentCache`

**时机**：某段 `subtreeHash` 变化，L2 lookup miss，单段 `fullCompileToHtml` 后。

```
fragment = extractSegmentOuterHtml(compiled, segment.idx)
cache.setL2(l2Key, { segmentIdx, html: fragment, subtreeHash, createdAt })
```

### 7.4 读取路径：组装 — `assembleFromSegmentCache`

**前置条件**（`compilePipeline.ts`）：

- L1 miss
- `input.baselineHtml` 非空（调用方 `lastCompiledHtmlRef`）
- `useCache !== false`

**算法**（`segmentAssembly.ts`）：

```
html = baselineHtml
for each segment in currentSegments:
  if segment.cacheable:
    cached = l2Store.get(buildL2Key(idx, subtreeHash))
    if cached → l2Hits++, continue   // baseline 已含该段，跳过

  // 变更段或不可缓存段
  minimalPage = rebuildPageForSegment(pageData, segment.idx)  // 保留 idx 路径！
  compiled = fullCompileToHtml(minimalPage)
  fragment = extractSegmentOuterHtml(compiled, segment.idx)
  html = replaceSegmentInHtml(html, segment.idx, fragment)    // 仅替换变更段
  recomputed++

return { html, l2Hits, recomputed }
```

**`rebuildPageForSegment`（`htmlSegments.ts`）**：裁剪 page 树，仅保留通向目标段的分支；路径外 sibling 用空 stub 占位，保证单段编译输出的 `node-idx-content.children.[n]` 与 baseline 一致。**不可折叠到 `children.[0]`**，否则 extract/replace 失败 → 降级全量 miss。

**`replaceSegmentInHtml`**：DOMParser 解析 baseline，按 `node-idx` 找段根，`replaceWith` 新片段 outerHTML。

### 7.5 L2 成功后回填 L1

组装成功 → `setL1(当前 pageKey, assembled.html)`，下次相同 page 可直接 L1 命中。

### 7.6 降级条件

| 条件 | 结果 |
|------|------|
| 无 `baselineHtml` | 跳过 L2，全量 miss |
| `assembleFromSegmentCache` 返回 null | `recordL2Miss()`，全量 miss |
| 多段全部重编译（`l2Hits===0 && recomputed===segments.length && length>1`） | 返回 null，改走一次全量更快 |
| extract/replace 失败 | 返回 null（结构变化或 idx 错位） |

### 7.7 性能实测（场景 3：L 档改背景色 5 次）

| 阶段 | `pipelineMs` 中位数 | `cacheHitLevel` | 说明 |
|------|---------------------|-----------------|------|
| 改造前 | 294.4 | `miss` | 每次全量编译 |
| L2 有 bug | ~406–459 | `miss` | idx 折叠 + 全段 replace，组装失败 |
| **改造后** | **21.7** | **`L2`** | ~33 段 L2 命中 + 1 段重编译 |

## 8. L3：运行时 DOM 保留

L3 **不经过 LruStore**，是「富文本输入期间跳过编译」的快捷路径。

### 8.1 快照结构 — `DomPreserveSnapshot`

```ts
{
  html: string;              // 冻结时的整页编译 HTML
  pageFingerprint: string;     // buildPageFingerprint(…)
  focusedAt: number;
}
```

### 8.2 写入 — `preserveDom`

**调用方**：`MjmlDomRender.tsx` 每次编译成功后（非拖拽中）：

```ts
lastCompiledHtmlRef.current = compiledHtml;
renderCache.preserveDom(compiledHtml, { pageData, profile: 'edit', dataSource });
```

### 8.3 读取 — `tryL3`

**调用方**：`compileWithRenderCache` 在 L1 之前：

```ts
if (l3Snapshot && buildPageFingerprint(current) === l3Snapshot.pageFingerprint)
  → return l3Snapshot.html, hitLevel: 'L3'
```

### 8.4 释放 — `releaseDomPreserve`

`MjmlDomRender` 在 `isTextFocus` 变为 false 时调用，退出富文本模式后走正常 L1→L2→miss。

### 8.5 与 MjmlDomRender 的配合

富文本聚焦时 `MjmlDomRender` effect **提前 return**，不调用 `compileWithRenderCache`，画布保留当前 DOM（配合 canvas-mount 与 L3 双保险）。

## 9. 完整缓存流程（端到端）

以 **编辑 Tab 改 section 背景色** 为例：

```
用户改色 → formState 更新 content
    ↓
MjmlDomRender effect（非 isTextFocus / 非 isDragging）
    ↓
content 同步 → 本地 pageData（cloneDeep）
    ↓
compileWithRenderCache({
  pageData,
  baselineHtml: lastCompiledHtmlRef.current,  // 上一帧整页 HTML
  profile: 'edit',
  dataSource: mergeTags,
})
    │
    ├─ tryL3 → miss（page 指纹已变）
    ├─ getL1(pageKey) → miss（page 内容已变）
    ├─ assembleFromSegmentCache
    │     ├─ 33 段 L2 hit → skip
    │     ├─ 1 段 recompute + replace
    │     └─ return html, l2Hits=33, recomputed=1
    ├─ setL1(pageKey, assembled.html)
    └─ return hitLevel: 'L2', pipelineMs ≈ 21ms
    ↓
lastCompiledHtmlRef = compiledHtml
preserveDom(compiledHtml)          // 更新 L3 快照
    ↓
mountEditCanvas(rawHtml, prevSegmentHashes)   // canvas-mount，与缓存正交
    ↓
prevSegmentHashesRef 更新
```

**冷启动（首次打开编辑器）**：

```
baselineHtml = '' → 跳过 L2
→ fullCompileToHtml(整页) → hitLevel: 'miss'
→ setL1 + seedL2FromFullHtml（34 段写入 L2）
→ lastCompiledHtmlRef = html
```

**Undo 回到历史快照**：

```
pageData 与某次历史完全一致
→ getL1(pageKey) hit → hitLevel: 'L1', ~0ms
→ 不访问 L2
```

## 10. 架构总览与模块职责

```
                    compileWithRenderCache()          ← compilePipeline.ts
                              │
         ┌────────────────────┼────────────────────┐
         ▼                    ▼                    ▼
    ┌─────────┐         ┌─────────┐         ┌─────────┐
    │   L3    │         │   L1    │         │   L2    │
    │tryL3 /  │ ──miss─▶│ getL1   │ ──miss─▶│assemble │
    │preserve │         │ l1Store │         │FromSeg  │
    └─────────┘         └─────────┘         └─────────┘
         │                    │                    │
         └──────────── miss：fullCompileToHtml ─────┘
                              │
                    setL1 + seedL2FromFullHtml
```

| 文件 | 职责 |
|------|------|
| `compilePipeline.ts` | L3 → L1 → L2 → miss 决策编排；回填 L1 / seed L2 |
| `RenderCacheManager.ts` | L1/L2 LRU 存储、L3 快照、统计、`seedL2FromFullHtml` |
| `lruStore.ts` | 通用 LRU Map |
| `hash.ts` | Key / 指纹计算 |
| `constants.ts` | 引擎版本、容量上限、段类型白名单 |
| `segments.ts` | `collectRenderSegments` |
| `segmentAssembly.ts` | L2 组装 `assembleFromSegmentCache` |
| `htmlSegments.ts` | `extractSegmentOuterHtml` / `replaceSegmentInHtml` / `rebuildPageForSegment` |
| `fullCompile.ts` | `JsonToMjml` + `mjml-browser`（无缓存读写） |
| `types.ts` | 入参/出参/条目类型定义 |

## 13. 引擎版本与缓存失效

修改块 render 实现或升级 `mjml-browser` 后，在 `constants.ts` 递增：

```ts
export const RENDER_ENGINE_VERSION = '1.0.2';
```

L1/L2 key 均含 `engine` 字段，旧条目自然 miss，无需手动 `clear()`。
